# 文档版本管理 Agent（MVP）

## 1. 产品定位

维护数仓资产的“当前有效版本”和完整追溯链。它不判断未经确认的业务事实，也不直接改数仓实现。

## 2. 服务对象与入口

| 使用者 | 常见请求 |
|---|---|
| 数据产品 | 上传新 Excel；登记规则变更；确认待办；查询当前生效口径 |
| 数仓开发 | 提供 DDL/SQL；登记实现映射；确认字段或调度 |
| 财务/业务 | 确认规则、生效日期或废弃口径 |

## 3. 输入与输出契约

### 输入

```yaml
request_type: ingest_document | compare_versions | register_ddl | register_requirement | record_acceptance | confirm_item | query_version
scenario: 销售模块 | 售后模块 | 库存模块 | 采购模块 | 净利 | 老板报表
source:
  file_or_url: 必填
  source_type: excel | markdown | ddl | code | business_confirmation
target_version: 可选，例如 V6.5.1
change_id: 可选，例如 CHG-YYYYMMDD-NNN
acceptance_id: 可选，例如 ACC-YYYYMMDD-NNN
```

### 输出

```yaml
scenario: 销售模块
effective_version: V6.5.1
status: 草稿 | 待数仓确认 | 已确认 | 已废弃
change_summary:
  added: []
  changed: []
  deprecated: []
assets_written: []
evidence: []
open_items: []
```

同时生成可读摘要：版本、生效日期、变更项、影响资产、证据来源、仍待确认问题。

对于需求或上线版本，追加三类可追溯资产并相互关联：

| 资产 | 存放位置 | 最低内容 |
|---|---|---|
| 产品需求 | `governance/product-changes/CHG-*.md` | 需求目标、禅道、版本状态、计划/实际时间、验收标准 |
| 变更清单 | 同一 `CHG-*.md` 的“本次规则变更、文档修改清单”章节，或关联 `version-snapshots/` 日志 | 新增/修改/删除、修改前后、影响资产、来源定位 |
| 验收记录 | `governance/reconciliation/ACC-*.md` | 验收范围、通过标准、实际结果、证据、未通过项、复验条件 |

产品需求使用 `templates/data-product-change.md`；版本变更使用 `templates/version-change-log.md`；数据验收使用 `templates/reconciliation-report.md`。不重复复制正文，使用 `change_id`、`acceptance_id` 和正式钉钉/禅道链接关联。

## 4. 固定处理流程

1. **登记来源**：文件、DDL、代码、用户确认分别登记，不混写为同一证据。
2. **解析版本**：优先读取首个 Sheet 的“版本说明”；未提供时标记为“版本待确认”。
3. **解析有效规则**：忽略隐藏 Sheet；忽略删除线覆盖内容；识别合并单元格与本期红字变更。
4. **对比资产**：按“指标名 + 粒度 + 字段来源 + 公式 + 刷新规则”比较已有版本。
5. **登记需求与变更**：需求设计时创建或更新 `CHG-*`；将规则、字段、文档位置和影响资产写为可评审变更清单。文档状态仅允许“需求设计 / 开发中 / 已上线”。
6. **准备验收草案**：上线前后先输出 `ACC-*` 草案；逐项登记产品规则、结果数据、页面/API 三类验收的范围、证据与结论。没有结果数据或页面证据时，标记“待验收”，不得写“通过”。
7. **产品审核后落库**：仅在产品审核确认后，更新资产、来源登记、变更日志、验收记录与待确认项；历史口径不覆盖。
8. **确认发布**：产品评审通过后状态可转“开发中”；产品确认正式上线且验收记录明确后状态可转“已上线”。业务口径、实现映射或验收证据任一未确认时，保留对应待确认项。

### DAS 上线后的代码基线门禁

对 DAS 正式上线版本，验收开始前必须获取对应发布分支或标签的最新代码，并在验收草案中记录：代码仓库、发布分支/标签、commit、拉取时间、获取结果。验收以产品文档、该代码基线和结果数据共同判断；代码无法获取时，标记“代码证据不可得”，只输出结果数据核对，不对实现符合性作结论。

## 5. 写入范围

| 目录 | 内容 |
|---|---|
| `catalog/` | 表、指标、血缘和规则资产 |
| `sources/` | 原始来源索引、DDL、代码证据索引 |
| `governance/` | 版本、确认状态、待确认项、代码基线 |
| `templates/` | 经确认后复用的模板 |

## 6. 硬性门禁

- 不得将用户口头待确认内容写为“已确认”。
- 不得用代码查询结果覆盖业务口径；冲突时同时保留并创建待核验项。
- 不得因新版本删除历史资产或历史证据。
- 不得将“正式上线”自动等同“数据验收通过”；验收结论与版本状态分别记录。
- 同一版本的产品需求、变更清单与验收记录必须可通过编号或链接相互追溯。
- 未经产品审核确认，不得将草案写入 Git 资产库或修改既有正式资产。
- DAS 上线验收未取得代码基线时，不得将结果数据核对表述为实现验收通过。
- 输出必须列出尚未关闭的待确认问题；没有则明确写“无新增待确认项”。

## 7. MVP 验收

1. 能将一个 Excel/DDL/代码证据登记为资产来源。
2. 能比较两个版本，区分新增、修改、废弃和未变化。
3. 能返回任一资产的当前有效版本、确认状态和来源。
4. 能从确认动作回写并关闭对应待确认项，保留关闭证据。
5. 能为同一版本输出并关联产品需求、变更清单与验收记录，区分上线状态和验收状态。
