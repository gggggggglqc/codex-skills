# 本地 ChatGPT Skill 向云端智能体迁移改造规范

版本：V1.1  
日期：2026-10-21  
适用对象：原本依赖本地电脑、数据库直连、本地文件或本地进程的 Skill，迁移到由云端智能体编排 Python 沙箱、SQL MCP 及文件上传等工具的运行环境。

## 1. 目的与核心结论

本规范是一份可独立使用的通用迁移标准。执行者不需要取得任何示例 Skill，只需结合待迁移 Skill 的实际文件和目标云端平台的工具契约，按本文完成盘点、设计、改造、验证和交付。

核心结论是：

> Skill 的云端迁移不是简单修改路径，也不是把本地脚本原样上传；本质上是重新划分执行责任：智能体负责编排工具，SQL MCP 负责数据库访问，Python 沙箱负责确定性的校验和计算，Skill 文档负责约束整个协议。

迁移时应尽量保持业务语义不变，改变的是运行方式、数据交接方式、失败策略和资源保护方式。

## 2. 云端运行前提

本规范默认云端智能体具备：

1. Python 执行沙箱工具；
2. SQL 执行工具；
3. Python 沙箱不能直接连接数据库或在其中执行数据库连接代码；
4. 智能体可以先调用 Python，再调用 SQL 工具，再把 SQL 结果交回 Python；
5. 如需生成文件，可使用平台提供的文件上传或对象存储工具。

迁移前必须先确认目标平台的真实能力，不能仅凭工具名称推断：

| 能力 | 必须确认的问题 | 对实现的影响 |
|---|---|---|
| Skill 文件访问 | Python 工具能否读取 Skill 目录中的脚本 | 决定采用多文件模块还是单文件运行时 |
| 脚本执行 | 能否按文件路径执行脚本 | 不能时需将完整源码作为一次代码提交执行 |
| 模块导入 | 是否允许导入同目录模块 | 不允许时需合并为自包含运行时 |
| 输入方式 | 是否支持 stdin、函数参数或仅支持 code 字符串 | 决定阶段载荷的传递接口 |
| 调用状态 | SQL 工具是否返回成功、截断、分页等原生状态 | 决定回执字段如何映射 |
| 数据限制 | SQL 长度、返回行数、响应大小、超时、Python 内存和时长 | 决定切片、分批及保护阈值 |
| 文件能力 | 是否可写临时文件、是否有上传工具 | 决定导出流程 |
| 状态持久化 | 两次 Python 调用之间是否保留变量和文件 | 默认按“不保留”设计 |

不得预设云端能够访问 Skill 文件、执行文件路径、导入同目录模块或读取 stdin。如果目标 Python MCP 支持这些能力，可以采用模块化运行时；如果只接收一次完整代码且看不到 Skill 文件，应采用单文件自包含运行时和类似 `run(request) -> result` 的函数入口，不得依赖文件路径、同级 import、stdin、当前工作目录或跨调用变量。

## 3. 迁移前常见做法与迁移后目标形态

| 维度 | 迁移前常见做法 | 迁移后目标做法 | 通用迁移要求 |
|---|---|---|---|
| 数据库访问 | Python 读取连接配置并通过数据库客户端库直连 | Python 只生成 SQL；智能体调用 SQL MCP | 移除数据库驱动、连接、游标、事务和凭据读取 |
| 执行主体 | 一个本地脚本包办查询、比对和输出 | 智能体在 Python 与 SQL MCP 之间编排 | 将外部副作用与纯计算解耦 |
| 输入 | 命令行参数、本地环境变量、`.env` | 明确参数加单一 JSON 阶段载荷 | 输入必须结构化、可校验、可复现 |
| 状态 | 同一进程内保存对象和数据库连接 | 每阶段显式携带上一步完整输出 | 默认无会话状态，不依赖隐式上下文 |
| SQL 结果 | 游标直接返回行 | SQL MCP 原始响应封装成带状态回执 | 必须校验成功、截断、分页、字段和行数 |
| 失败策略 | 异常或局部结果可能在同一脚本中继续 | 任一回执异常立即停止，不使用部分结果 | 必须 fail-closed，禁止猜测和部分计算 |
| 规模控制 | 主要靠查询批次参数 | 时间切片、批次、查询数、行数、载荷大小均设硬上限 | 所有限制应显式、可审计、越界即停止 |
| 类型处理 | 数据库驱动返回 datetime、Decimal 等对象 | SQL 侧将时间和数值抹平，Python 兼容 JSON/repr | 工具边界使用稳定、可序列化类型 |
| 文件输出 | 直接写用户桌面 CSV | Python 返回 CSV 文本，智能体调用上传工具 | 不依赖本地桌面或固定路径 |
| 代码组织 | 多个脚本重复公共逻辑 | 公共协议模块 + 业务模块 + 统一入口 | 抽取公共协议，保留场景配置和功能差异 |
| 业务文档 | 大量规则集中在 `SKILL.md` | `SKILL.md` 管编排，`reference/` 管场景口径 | 分离通用执行协议和场景业务规则 |
| 返回契约 | 主要是终端文本和文件路径 | JSON 结果、统计口径、方向和 validation | 输出字段及含义必须固定 |

## 4. 必须遵守的迁移原则

### 4.1 业务语义优先，先冻结再改造

改造前先建立“原技能业务基线”，至少记录：

- 触发场景和不应触发的场景；
- 必填输入、默认值和歧义处理；
- 数据源、表、字段、过滤条件和状态枚举；
- 时间口径、时区、闭区间或开区间；
- 业务键、聚合规则、数量/金额公式和结果方向；
- 空值、零值、单边数据、重复记录的处理方式；
- 输出字段、文件格式、排序和失败原因；
- 原技能已知限制与已有测试。

迁移的默认目标是“业务等价、运行架构变化”。如果发现原技能存在缺陷，不应静默修正；应单独列出“迁移必需修复”和“业务口径变更”，取得确认后再改变业务语义。

### 4.2 数据访问与计算彻底分离

Python 沙箱不得包含：

- 数据库驱动和连接代码；
- 数据库地址、账号、密码或 `.env` 加载；
- 游标、事务、提交、回滚；
- 通过网络绕过 SQL MCP 访问数据库；
- 让用户提供数据库凭据给 Python。

职责应固定为：

- Python：参数校验、生成查询计划、解析和校验回执、业务计算、生成结构化结果或文件内容；
- 智能体：按计划调用工具、保留原生状态、组装阶段载荷、控制流程；
- SQL MCP：执行受控的只读 SQL 并返回原始结果和执行状态；
- 上传工具：在用户明确需要文件时接收内容并返回可下载地址。

### 4.3 采用“计划—执行—验证—计算”闭环

每个需要外部数据的阶段均应采用相同协议：

1. Python 根据已校验的输入生成 `queries` 和 `manifest`；
2. 智能体严格按计划调用 SQL MCP；
3. 智能体不改写业务行，将工具原始响应和原生状态封装为回执；
4. Python 校验 `manifest + responses` 的完整性；
5. 仅在全部查询验证通过后计算阶段结果；
6. 若还需下钻，输出下一阶段的查询计划；否则输出最终结果。

最小查询描述建议包含：

```json
{
  "query_id": "primary:source_a:1",
  "source": "source_a",
  "db_name": "database_name",
  "sql": "SELECT ...",
  "time_slice": {
    "index": 1,
    "start_time": "YYYY-MM-DD HH:MM:SS",
    "end_time": "YYYY-MM-DD HH:MM:SS"
  },
  "required_columns": ["key", "total_num"],
  "row_limit": 2000
}
```

最小 SQL 回执建议包含：

```json
{
  "query_id": "primary:source_a:1",
  "success": true,
  "truncated": false,
  "has_more": false,
  "raw": "<SQL 工具原始响应>"
}
```

`raw` 只能做外层 JSON 转义，不得让智能体先解析、筛选、补字段或重新汇总。若 SQL 工具没有上述同名状态字段，应在迁移设计中记录可靠的映射方式并做真实工具验证；不得凭返回内容猜测执行是否完整。

### 4.4 默认无状态，所有阶段输入显式传递

不得依赖：

- 上一次 Python 调用留下的变量；
- 临时文件在下一次调用仍存在；
- 固定当前工作目录；
- 本地绝对路径；
- 智能体“记得”此前未结构化的数据；
- 查询失败后从中间阶段自动续跑。

每个阶段必须能够只凭本次输入重现。任务中断、回执丢失或校验失败时，从最近一个可证明完整的阶段重新开始；无法证明时从查询计划重新开始。

### 4.5 严格完整性校验，失败时关闭而不是降级

进入计算前至少校验：

- `query_id` 非空、唯一并属于当前 manifest；
- 每条计划查询有且仅有一个回执；
- 不存在未计划的额外回执；
- `success=true`；
- 结果未截断且无后续页，或已按明确分页协议取全；
- 原始响应可解析；
- 每行是对象且包含全部必填列；
- 行数、总行数和载荷大小未越界；
- 上游阶段含完整 `validation`，计划数等于已验证数；
- 上游输出的业务类型、时间范围和规则标识与当前请求一致。

任何一项失败时：

- 立即停止当前链路；
- 明确报告阶段、`query_id` 和原因；
- 不使用部分结果；
- 不生成业务结论；
- 不生成或上传结果文件；
- 不自动把失败、空响应或解析异常当成零行。

### 4.6 资源保护必须显式并可解释

每个迁移后的 Skill 都要根据实际平台能力定义：

- 最大业务时间范围；
- 单个时间片大小和最大时间片数；
- 单条查询最大返回行数；
- 最大查询数；
- 单次二级查询最大业务键数量和批次大小；
- 所有阶段累计最大行数；
- 单次阶段载荷最大字节数；
- SQL 最大长度；
- Python 执行时长和内存预算；
- 文件最大大小与上传限制。

建议在 SQL 中使用 `LIMIT = 允许上限 + 1` 作为哨兵：返回第 N+1 行时不是截掉继续算，而是明确失败并要求缩小范围。

本文不规定通用数值。每个 Skill 必须根据业务数据量、SQL 工具限制、Python 沙箱限制和业务容忍度独立确定阈值，并记录确定依据。

### 4.7 工具边界只传输稳定类型

不同工具可能把 datetime、Decimal 或大整数返回为非标准 JSON。迁移时应优先在 SQL 中规范化：

- 时间字段格式化为明确字符串；
- 聚合数值转换为字符串；
- 空值规则显式化；
- 字段名使用稳定别名；
- 不依赖数据库驱动私有对象类型。

Python 内部涉及数量、金额或比例时应使用 `Decimal` 等精确类型，输出 JSON 时再转字符串；不要用二进制浮点替代原有精度语义。

### 4.8 SQL 必须受控、只读并可审计

- SQL 必须由代码模板生成，不允许把用户整段文本直接拼成 SQL；
- 字符串字面量必须转义，枚举、数据库名、表名和排序字段使用白名单；
- 若 SQL MCP 支持参数化查询，优先参数化；不支持时使用集中封装的安全字面量函数；
- 每条查询明确数据库、数据源、必填列和行数上限；
- 只使用平台允许的只读语句；
- 遵守工具对分号、注释、SQL 长度和多语句的限制；
- 分页必须有稳定排序、去重或快照策略；无法证明跨页一致时应缩小查询范围，而不是冒险拼接。

### 4.9 文件输出改为“内容生成 + 云端上传”

移除桌面路径、用户目录、`open(..., "w")`、`os.makedirs` 等本地输出逻辑。推荐流程：

1. Python 返回 `file_name`、`content`、`content_type` 等文件描述；
2. 智能体在用户明确要求导出时调用上传工具；
3. 上传成功后返回下载地址；
4. 上传失败不应宣称已生成可下载文件。

默认直接返回结构化结果；只有用户明确要求文件，或结果量确实不适合消息展示时才导出。

### 4.10 文档是运行时协议的一部分

`SKILL.md` 至少要说明：

- 准确的触发条件和排除条件；
- 执行前必须确认的输入；
- 实际可用工具及各自职责；
- 完整编排步骤；
- 查询描述、manifest、回执和阶段载荷结构；
- 停止条件、失败文案和是否允许重试；
- 资源保护边界；
- 最终结果契约；
- 文件导出行为；
- 场景规则的来源和优先级。

复杂 Skill 应将业务规则拆到 `reference/`：`SKILL.md` 负责通用编排和安全协议，各 reference 负责场景的表、字段、过滤、枚举、例外和失败原因。发现文档与代码不一致时必须停止并报告，不得由智能体自行选择一个版本。

## 5. 标准改造方法

### 阶段一：盘点与基线

1. 递归读取原 Skill 的全部文件；
2. 列出入口、脚本、依赖、环境变量、绝对路径、网络访问、本地文件、子进程和数据库连接；
3. 建立“场景—输入—数据源—计算—输出—失败”矩阵；
4. 记录真实业务规则和原测试覆盖；
5. 将业务缺陷与运行环境不兼容问题分开列出；
6. 确认目标云端工具契约及限制。

交付物：迁移盘点表、业务基线、云端能力矩阵、待确认问题。

### 阶段二：设计目标架构

1. 选择多文件模块或单文件自包含运行时；
2. 设计统一入口；
3. 把数据库调用改为“生成查询计划”；
4. 定义 manifest、回执、阶段载荷和结果 JSON；
5. 按业务需要设计主查询、二级查询、补充查询和导出等阶段；
6. 定义硬上限和失败策略；
7. 明确工具编排由 `SKILL.md` 驱动。

交付物：运行时契约和阶段状态图。

### 阶段三：改造代码

1. 先抽取公共校验、类型转换、查询描述、回执验证和输出函数；
2. 将原 `fetch_*` 直连函数拆为 SQL 生成函数和结果消费函数；
3. 把重复业务脚本按共同模型合并为配置化模块，但保留功能差异；
4. 所有外部输入先校验再用于 SQL；
5. 所有数据消费阶段只接受一个完整结构化载荷；
6. 结果中加入 `validation`，记录计划数、验证数、时间片、各来源行数和载荷大小；
7. 文件写入改为内存内容输出；
8. 删除本地直连、凭据、绝对路径、子进程和隐式状态依赖。

### 阶段四：改造文档

1. 精简 frontmatter，确保 `name`、`description` 与真实触发范围一致；
2. 删除本地电脑专属命令和用户名路径；
3. 写清工具职责和禁止事项；
4. 写清每个阶段的输入、输出和停止条件；
5. 将场景规则拆到 reference，并声明覆盖关系；
6. 写清默认是否查实时数据、默认是否导出文件；
7. 写清空结果、无可操作结果、失败和超限的行为。

### 阶段五：验证

验证必须分层，不能把本地测试等同于云端可用：

1. 静态验证：语法、frontmatter、链接、无禁用依赖、无密钥和绝对路径；
2. 纯函数测试：业务计算、精度、键合并、排序和文件渲染；
3. 协议测试：缺失/重复/额外回执、失败、截断、分页、错误对象、缺字段、超行、超载荷；
4. 业务等价测试：同一组固定输入下，原实现和迁移后实现的业务结果一致；
5. 空结果、缺失结果和稀疏数据测试：尤其验证“无响应不等于零”；
6. 边界测试：最大时间范围、最大批次、N+1 行哨兵和最大业务键数量；
7. 云端 Python MCP 冒烟：验证真实输入方式、模块/文件可见性和输出大小；
8. SQL MCP 冒烟：执行最小只读查询，验证数据库选择、响应格式和原生状态；
9. 端到端冒烟：由真实智能体完成“计划—SQL—回执—计算”完整链路；
10. 生产规模和权限验证：单独记录，未验证时不得宣称生产就绪。

### 阶段六：最小化交付

部署 Skill 目录只保留运行所需内容。开发期测试、构建脚本、迁移报告、样例大数据、缓存、压缩包和备份应放在 Skill 目录外。

推荐多文件结构：

```text
skill-name/
├─ SKILL.md
├─ reference/
│  ├─ runtime-contract.md       # 可选：协议较长时拆出
│  └─ scenario-*.md
└─ scripts/
   ├─ run_skill.py              # 统一入口
   ├─ common.py                 # 校验、协议、类型、限额
   └─ domain_*.py               # 业务 SQL 生成与纯计算
```

仅代码字符串执行的沙箱推荐结构：

```text
skill-name/
├─ SKILL.md
├─ reference/
│  ├─ runtime-contract.md
│  └─ scenario-*.md
└─ scripts/
   └─ sandbox_runtime.py        # 自包含，无同级 import、文件或 stdin 依赖
```

## 6. 通用阶段接口建议

简单 Skill 可以只有一次查询阶段；复杂 Skill 可按业务需要使用以下通用阶段：

```text
确认输入
  → plan-primary
  → SQL MCP 执行主查询
  → consume-primary
  → 若已满足完成条件则结束
  → 可选 plan-secondary
  → SQL MCP 执行二级查询
  → 可选 consume-secondary
  → 可选 plan-enrichment / consume-enrichment
  → finalize
  → 可选 render-file / upload
```

建议所有阶段输出都包含：

```json
{
  "status": "ok",
  "stage": "consume-primary",
  "request_scope": {},
  "result": {},
  "next_queries": [],
  "validation": {
    "planned_query_count": 3,
    "verified_query_count": 3,
    "source_row_counts": {},
    "payload_bytes": 1234
  }
}
```

如果为了兼容现有 Skill 不增加统一 `status/stage/result` 外壳，仍必须保证每阶段的实际字段稳定，并在 `SKILL.md` 中逐项定义。

## 7. 哪些内容可以复用，哪些不能照搬

### 可作为通用模式复用

- 智能体编排、SQL MCP 取数、Python 纯计算的职责划分；
- manifest 与一一对应回执；
- 原生成功/截断/分页状态校验；
- 单一结构化载荷；
- fail-closed 和不使用部分结果；
- 类型抹平、Decimal 精确计算；
- 时间切片、批次、LIMIT+1、载荷上限；
- 内存生成文件内容后调用上传工具；
- `SKILL.md` 与场景 reference 分层；
- 部署包最小化和真实 MCP 冒烟。

### 每次迁移都必须重新确定

- 业务表、字段、过滤、枚举、计算规则和结果方向；
- 地域、实例、数据库、工具名称及调用参数；
- 时间范围、切片大小、行数、查询数和载荷大小等阈值；
- 阶段数量、阶段顺序以及是否需要二级查询或补充查询；
- 输出格式、字段和失败原因枚举；
- 是否允许自动查询、自动导出或自动重试；
- 是否需要文件系统、网络、浏览器或其他外部工具。

## 8. 验收清单

### 8.1 业务等价

- [ ] 所有原有能力均有对应入口；
- [ ] 输入、时间、过滤、聚合、精度和结果方向已逐项核对；
- [ ] 空值、零值、缺失记录和重复记录的行为已确认；
- [ ] 业务变更与纯迁移变更已分开记录；
- [ ] 文档口径与代码一致。

### 8.2 云端兼容

- [ ] Python 不直连数据库；
- [ ] 不读取数据库凭据或 `.env`；
- [ ] 不依赖本地绝对路径、桌面、固定用户目录或子进程；
- [ ] 不依赖跨调用变量或持久化临时文件；
- [ ] 输入方式与真实 Python MCP 契约一致；
- [ ] 多文件/单文件形态与沙箱文件可见性一致；
- [ ] 文件导出使用云端上传能力。

### 8.3 数据完整性与安全

- [ ] SQL 只读、模板化并限制动态字段；
- [ ] query_id 唯一且回执一一对应；
- [ ] 失败、截断、分页和解析异常均会停止；
- [ ] 不会把错误或缺失响应当成空结果；
- [ ] 必填列、行数、总量和载荷大小已校验；
- [ ] 不会在前序失败后生成结论或文件；
- [ ] Skill 内无密钥、令牌和真实凭据。

### 8.4 性能与可运维性

- [ ] 已定义时间、查询、行数、批次、载荷和执行时长上限；
- [ ] 超限提示能指导用户缩小范围；
- [ ] 结果含 validation，可定位执行完整性；
- [ ] 错误信息包含阶段和查询标识，但不泄露凭据；
- [ ] 真实 Python MCP、SQL MCP 和端到端链路均已冒烟；
- [ ] 对未完成的生产规模、权限或并发验证有明确声明。

### 8.5 交付包

- [ ] `SKILL.md` frontmatter 合法；
- [ ] 所有链接和文件名一致；
- [ ] 只包含运行必需文件；
- [ ] 无 `__pycache__`、`.pyc`、日志、测试数据、归档和备份；
- [ ] 开发测试保留在部署目录外；
- [ ] 已记录版本、变更点、验证证据和剩余风险。

## 9. 常见错误做法

1. 只把数据库地址从 localhost 改成云地址，仍让 Python 直连；
2. 把 `.env`、凭据或本地配置一起上传；
3. 让智能体自由拼 SQL，而不是让代码生成受控查询计划；
4. 只传 SQL 结果，不传成功、截断和分页状态；
5. 某条查询失败后继续用其余数据得出结论；
6. 把解析失败、超时或空字符串当成零行；
7. 假设 Python 沙箱能访问 Skill 文件或保留上次变量；
8. 在多个 stdin、多个临时文件或多次对话之间隐式拼接状态；
9. 直接写“桌面文件路径”，但云端用户无法访问；
10. 为了迁移顺便改变业务口径，却没有单独说明和验收；
11. 把本地单元测试通过写成“生产环境已验证”；
12. 把大量测试、构建、报告和缓存塞进最终 Skill 包。

## 10. 迁移完成的定义

只有同时满足以下条件，才可以把 Skill 标记为“已完成云端迁移”：

1. 业务基线已建立，业务等价或已批准的变更有证据；
2. Python 已完全移除数据库直连和本地机依赖；
3. 智能体、SQL MCP、Python 沙箱和上传工具的职责清晰；
4. 阶段输入输出、manifest、回执和失败策略均已文档化；
5. 任何不完整数据都不能产生业务结论；
6. 资源限制和越界行为明确；
7. 本地静态/协议/业务测试通过；
8. 真实云端 Python MCP 与 SQL MCP 端到端冒烟通过；
9. 最终交付包最小、无凭据、无缓存、无本地路径；
10. 未验证的生产规模、并发、权限和外部上传能力被明确列为剩余风险。
